## 0. 本轮最重要的发现：视频管线从来不可能跑通

`src/aniflow/agnes/video.py` 的 `retrieve()` 读取结果地址时用的是：

```
data["metadata"]["url"]
```

但 Agnes 官方文档的 completed 响应里**根本没有 `metadata` 这个对象**，播放地址是**顶层 `url` 字段**。

后果：任何一个视频生成成功后，都会走到 `raise AgnesApiError("Video completed but metadata.url is missing")`。
**100% 失败，无一例外。**

为什么测试没发现：`tests/test_candidates.py` 直接 mock 了 `VideoResult(video_url=...)` 对象，
**完全绕过了出 bug 的解析函数**。测试测的是 mock，不是代码。

> 这解释了为什么项目开发了 170 次提交却从未产出一条视频。
> **已修复，并补了 3 个用官方原始 payload 的回归测试。**

## 1. 你的三个问题：确定答案

### Q1：项目里是否已有多 Key 首尾帧抽卡？——有，但很脆弱，已重建

**原实现**（`pipeline/candidates.py`）的设计思路是对的：每个账号至少抽一次，再轮询补足，全部并发。
但有四个生产级致命缺陷：

| 缺陷 | 后果 |
|---|---|
| **创建与轮询耦合在一起** | 进程一崩，`video_id` 就丢了。**任务还在服务器上跑、配额已经花掉，但你拿不回结果** |
| **无限流** | 9 个 Key × 5 抽 = 45 个并发请求（Agnes 系工具实测约 16 req/min 上限）→ 免费额度变成一堆失败 |
| **创建无重试** | 一次网络抖动就静默少一张卡 |
| **无断点续跑** | 中断后重跑 = 从零重抽，配额白烧 |

**新引擎 `pipeline/gacha.py`：两阶段执行**

```
阶段一  提交所有抽卡 → 每拿到一个 video_id 立刻落盘
        ─────────── 此后任何崩溃都不会丢任务 ───────────
阶段二  逐个轮询取回结果
```

| 改进 | 说明 |
|---|---|
| 两阶段 + 账本落盘 | 原子写入，随时可杀可续 |
| 令牌桶限流 | 默认 16 req/min，请求均匀摊开而非爆发 |
| 每 Key 并发上限 | 默认 2，避免单账号被限速 |
| 创建重试 | 默认 3 次，指数退避 |
| **轮询超时不判死** | 任务可能仍在服务端跑完，`resume()` 能捡回来，不浪费配额 |
| 终态不重抽 | 重跑同一镜头不会再花配额 |
| 支持单帧 | 官方只要求首尾帧**至少有一个**，原代码强制要两个 |
| 时长可变 | 每个镜头独立 4–12 秒 |

**16 个新测试全部通过；全量 61 个测试通过。**
⚠️ 全部为离线 mock 测试，**未经真实 Agnes API 验证**。

### Q2：首尾帧之间能不能加中间帧？——**不能，官方不支持**

我核对了 `agnes-video-2.5` 和 `agnes-video-2.5-flash` 的完整官方参数表。
`keyframe` 模式**只有两个**媒体参数：

| 参数 | 说明 |
|---|---|
| `first_frame` | 首帧图 URL |
| `last_frame` | 尾帧图 URL |

原文：*"Provide this, `last_frame`, or both."* —— **没有任何中间帧参数。**

**你的记忆很可能来自 `agnes-video-v2.0`** —— 旧 AGENTS.md 里确实写了它有
"old multi-keyframe behavior"（多关键帧）。但**那个模型已经从 Agnes 官方下架了**，
文档索引和定价页都查不到。

#### 但这个限制其实不该绕过，而该顺着走

能塞中间帧的替代方案是 `reference` 模式（最多 5 张图），但它：
- 与 `keyframe` **互斥**（传了 `images` 就不能传 `first_frame`/`last_frame`）
- 官方明确说它会 *"recompose or retime"* —— **不保证精确对齐**，只是"参考"

**更好的解法：把一个长镜头拆成两个短镜头。**

```
想要：  A ──── M ──── B     一段 12 秒，中间过 M
实际：  A ──── M           镜头1，6 秒，首尾帧精确锁定
        M ──── B           镜头2，6 秒，首尾帧精确锁定
```

这样 M 从"一个不保证的参考"变成**两次精确锁定的帧**，控制力**更强**而不是更弱。
代价只是多一个剪辑点 —— 而搞笑短片本来就需要剪辑节奏。

> **结论：中间帧不支持，但「多镜头 + 每镜头首尾帧」是更优解，不是妥协。**
> 这也正好印证了接管审计里"改用可变镜头表"的建议。

### Q3：Arena 的视频生成能用吗？——**不能用于生产，但是很好的免费选型工具**

官方帮助文档（help.arena.ai）确认：

| 限制 | 实际影响 |
|---|---|
| **每 24 小时只能生成 2 条** | 抽卡需要几十条，直接出局 |
| **只有 Battle 模式** | 随机配对两个匿名模型，**你无法指定用哪个模型** |
| 不支持 Side-by-Side / Direct | 无法固定模型 = 无法保证风格一致 |
| **没有公开 API** | 无法程序化调用，无法进流水线 |
| 只能上传 1 张图，**且无法指定它是首帧还是尾帧** | 首尾帧控制完全做不到 |
| 时长 5–8 秒 | 比 Agnes 的 4–12 秒还窄 |
| 部分模型不出音频，且随机 | 结果不可预期 |

**判定：Arena 视频不能作为 AniFlow 的生产后端。** 差距不是一点点，是数量级。

**但它有一个真实用途：免费的模型选型实验台。**

你可以用它每天 2 次机会，专门测一件事：
> **"哪个视频模型最会做毛毡定格风格的猫？"**

投完票会揭晓模型名。攒上一两周，你就知道市面上谁最适合这个风格——
等 Agnes 免费期结束、或者质量不够时，你**已经知道该往哪儿去**，而不是临时抓瞎。

## 2. 风格决策：毛毡定格 —— 我强烈支持，而且理由比"好看"硬得多

你的直觉是对的，但真正的理由比"真人质量不行"更深。

### AI 视频最大的技术弱点，恰好是定格动画的美学特征

| AI 视频的失败模式 | 毛毡定格如何"吸收"它 |
|---|---|
| **时序抖动**（帧间闪烁、形变、漂移） | 定格动画**本来就是一格一格跳的**。抖动被读成风格，不是瑕疵 |
| **精细结构出错**（手指、牙齿、五官微表情） | 毛毡是**低频材质**，本来就没有精细结构可错 |
| **恐怖谷** | 毛毡玩偶是**公认的非写实**，观众不会用真人标准苛求它 |
| **720P 分辨率上限** | 毛毡纹理空间频率低，**720P 完全够用**，不浪费 |
| 抖音明令禁止"人物穿模" | 写实人物最容易穿模；毛毡体块简单，风险低得多 |

**换句话说：选毛毡不是退而求其次，是把模型的短板变成风格。**

### 额外的三个好处

1. **周边天然成立** —— 毛毡玩偶是现成的实物商品，IP 衍生不需要重新设计
2. **文化credibility** —— 阿凡提（上美影木偶动画）在国内有强烈的怀旧认同，画风自带"正经做动画"的信号，有利于对抗"AI 糊弄"的观感
3. **与既有工作一致** —— 项目原 benchmark 三风格里本来就有 needle-felt（毛毡），不是推倒重来

### 建议锁定

> **主风格：毛毡定格动画（needle-felt stop-motion）**
> 猫用毛毡最自然 —— 真实的毡化羊毛本来就有绒毛感，和猫的毛发是同一种视觉语言。

黏土（clay）作为备选，但毛毡对猫更优。

## 3. CapCut / Seedream：我收回删除建议

接管审计里我建议删掉 CapCut，**那个判断是错的，我当时只读了文档，没有你的实际使用数据。**

你的信息改变了结论：
- Seedream 4.3 / 4.0s 你已经**免费用了一年多**
- 效果**持续变好**
- 这是一年的真实产出经验，比我读官方文档的推断可靠得多

**修正后的方案：保留 Seedream，但改变接入方式。**

| | 原方案 | 修正方案 |
|---|---|---|
| Seedream 地位 | 一等图片源 | **仍是一等图片源** ✅ |
| 接入方式 | 全自动浏览器操控（登录态、选择器、探针） | **半自动导入**：你在 CapCut 正常出图 → 丢进监控目录 → AniFlow 自动收编、命名、上传公网、接入镜头表 |

**为什么改接入方式而不是改模型**：出问题的从来不是 Seedream，是"用程序去操控一个会改版的网页"。
那部分是永久维护负债，而且**它并没有为你省下多少时间**——你本来就在用 CapCut 出图，
真正费时的是"把图搬进流水线"，而半自动导入把这一段自动化了，风险却接近零。

如果将来确实需要全自动，可以再补，但不该是现在的优先级。

## 4. 文本层：GLM 5.3 走浏览器 → 架构必须解耦

你用 Tabbit 多账号在浏览器里跑 GLM 5.3，**这意味着没有 API**。

现有代码假设编剧/QA 都是 API 调用，这个假设对你的实际工作方式不成立。

**应对：文本层做成双通道。**

```
通道 A（你现在的方式）：浏览器里生成 → 粘贴/导入结构化脚本 → AniFlow 接手
通道 B（以后有 API 时）：直接调 API
```

关键是**中间格式**要先定下来：一个镜头表 JSON（含 Fact Pack、台词、分镜、首尾帧描述）。
定了它，上游用 GLM、Agnes 还是 ChatGPT 都无所谓，下游完全不用改。

这条同时服务了审计里说的"为中英双语预留结构"。
